# Threat model

One entry per edge case from the project spec. Each entry states the mechanism AgentGuard uses to close it and which phase (see [ROADMAP.md](ROADMAP.md)) implements it. "Mitigated by design, not yet tested" is an honest intermediate state — the goal is for every row to eventually have both a mechanism and a corresponding case in [EVALUATION.md](EVALUATION.md).

| # | Edge case | Mechanism | Phase |
|---|---|---|---|
| 1 | Prompt injection tells the agent to ignore policy | Policy is enforced in the gateway/broker, entirely outside the LLM's context; retrieved/generated content is never treated as a source of identity or authorization | 1 (enforcement), 2 (adversarial test) |
| 2 | Spoofed `agent_id`/`tenant_id` in the request | Identity is derived from authenticated transport-layer context (verified workload identity), never from request body fields | 1 (enforcement), 2 (adversarial test) |
| 3 | Policy changes while an approval is pending | Approval row stores `policy_version` and `action_hash` at creation; execution re-validates both match the *current* active policy before consuming the approval | 1 |
| 4 | Approval token replay | Atomic one-time `consumed_at` write (single UPDATE with a status-guarded WHERE clause); a second consumption attempt fails | 1 (enforcement), 2 (adversarial test) |
| 5 | Tool succeeds but gateway times out | Broker timeout returns immediately; the gateway then asks the target system (by idempotency record) whether the write happened: applied → success, read-only → failure with no side effect, not observed → stays `timeout` with an incomplete trace. A retry with the same key reconciles again and never re-executes. Known gap: a retry with a *new* key can still duplicate a late-landing write (see ROADMAP Phase 4) | 4 (implemented) |
| 6 | Policy service outage | Any exception during policy evaluation denies the call; approved calls aren't executed during an outage. The only fallback, `ALLOW_READS_WHEN_POLICY_UNAVAILABLE` (off by default), allows `read`-class tools only | 4 (implemented) |
| 7 | Gateway bypass (agent calls the real tool directly) | Target systems require a scoped credential on every call; only `agentguard.broker` can obtain one (static inventory test), and the agent SDK never loads the broker. This is a code-level guarantee in the single-process demo — runtime prevention needs the broker deployed separately with network policy (not done) | 4 (implemented in-process) |
| 8 | Audit tampering | The application has no update/delete code paths for `audit_events`, and `sql/postgres_audit_role.sql` revokes UPDATE/DELETE/TRUNCATE on that table from the app's own DB role for production Postgres, making it DB-enforced rather than just a code convention. Scope: protects against a misused app connection, not a privileged DB superuser or role reassignment — no "unbreakable log" claim. Not applied to SQLite dev/test runs (no equivalent grant model) | 1 (code path), 5 (DB grant) |
| 9 | Sensitive data in traces | `executions` and `audit_events` store only hashes of request/result payloads; full arguments live in the separately-restrictable `request_payloads` table; OTel span attributes carry identifiers and decisions only (tested) | 1, 4 |
| 10 | Duplicate tool call | Gateway dedupes on (agent, idempotency key); the target system dedupes on the execution id, which is globally unique — agent-supplied keys aren't, so two agents' keys can't collide downstream (tested) | 1, 4 |
| 11 | Confused deputy (broker misuses its own privilege) | Broker only acts on a decision the policy engine already produced, and each executor gets a credential for one scope only, enforced by the target system — the refund executor cannot create tickets (tested) | 1, 4 |
| 12 | Approval from wrong tenant/role | Approver identity and authority are checked server-side against the execution's tenant/role requirement, not trusted from the approval request itself | 1 (enforcement), 2 (adversarial test) |
| 13 | Schema drift on tool arguments | **Not implemented.** Tools carry `schema_version` and `input_schema`, but the gateway does not yet validate arguments against them, so unknown fields pass through to executors. Planned for Phase 5 | — |
| 14 | Agent loop / tool-call spam | Per-agent rate limit, rolling spend budget, circuit breaker on repeated denials, per-agent suspend, and a global kill switch; plus broker timeouts as per-call deadlines (all tested) | 4 (implemented) |
| 15 | Model update changes agent behavior | Regression suite (routine + adversarial cases) required to pass before any prompt/model/tool/policy change ships | 2 |
| 16 | Replay accidentally triggers a real action | Three layers: (a) `agentguard.replay` never imports `agentguard.broker` or the gateway service, verified by a test that inspects loaded modules in a fresh interpreter; (b) tool steps run through dry-run adapters only; (c) the CLI's DB connection is read-only at the database level (`PRAGMA query_only` / `READ ONLY` transactions) | 3 (implemented) |
| 17 | Clock skew / missing trace segments | `trace_complete` is explicitly computed and false when a segment is missing (e.g. unresolved timeouts), and events correlate by execution id. Only one clock (the gateway's) is recorded today — separate event vs. ingestion times aren't | 1 (partial) |
| 18 | Partial failure in a multi-step workflow | **Not implemented.** Each tool call is an independent execution; there's no workflow grouping, per-step state across calls, or compensation yet | — |

## Non-claims

This system does not claim to be "the first AI agent security platform" or to produce an "unbreakable audit log." The audit mechanism reduces tampering risk through restricted write permissions and (optionally, later) external immutable storage — it does not claim to stop every privileged attacker, and that limitation should stay stated plainly in any writeup.
