# Threat model

One entry per edge case from the project spec. Each entry states the mechanism AgentGuard uses to close it and which phase (see [ROADMAP.md](ROADMAP.md)) implements it. "Mitigated by design, not yet tested" is an honest intermediate state — the goal is for every row to eventually have both a mechanism and a corresponding case in [EVALUATION.md](EVALUATION.md).

| # | Edge case | Mechanism | Phase |
|---|---|---|---|
| 1 | Prompt injection tells the agent to ignore policy | Policy is enforced in the gateway/broker, entirely outside the LLM's context; retrieved/generated content is never treated as a source of identity or authorization. Exercised with a real Claude agent reading helpdesk tickets that carry injections (`agentguard.agents.support_agent`); `agentguard.evaluation.live_agent` reports what the model *attempted* separately from what *executed*, and fails if anything unsafe executed | 1 (enforcement), 2 (adversarial test), 7 (real agent) |
| 2 | Spoofed `agent_id`/`tenant_id` in the request | Identity is derived from authenticated transport-layer context (verified workload identity), never from request body fields | 1 (enforcement), 2 (adversarial test) |
| 3 | Policy changes while an approval is pending | Approval row stores `policy_version` and `action_hash` at creation; execution re-validates both match the *current* active policy before consuming the approval | 1 |
| 4 | Approval token replay | Atomic one-time `consumed_at` write (single UPDATE with a status-guarded WHERE clause); a second consumption attempt fails | 1 (enforcement), 2 (adversarial test) |
| 5 | Tool succeeds but gateway times out | Broker timeout returns immediately; the gateway then asks the target system (by idempotency record) whether the write happened: applied → success, read-only → failure with no side effect, not observed → stays `timeout` with an incomplete trace. A retry with the same key reconciles again and never re-executes. Known gap: a retry with a *new* key can still duplicate a late-landing write (see ROADMAP Phase 4) | 4 (implemented) |
| 6 | Policy service outage | Any exception during policy evaluation denies the call; approved calls aren't executed during an outage. The only fallback, `ALLOW_READS_WHEN_POLICY_UNAVAILABLE` (off by default), allows `read`-class tools only | 4 (implemented) |
| 7 | Gateway bypass (agent calls the real tool directly) | Target systems require a scoped credential on every call. The broker runs as its own service (`agentguard.broker.server`) and is the only process given target credentials; in Kubernetes, default-deny network policies let only the broker reach the target and only the gateway reach the broker (`deploy/helm`). `tests/integration/test_live_stack.py` runs helpdesk, broker and gateway as separate processes and shows the gateway's environment holds no credential the target accepts. Within the codebase, only `agentguard.broker` can obtain a credential (static inventory test) | 4, 8 (separate service + network policy) |
| 8 | Audit tampering | The application has no update/delete code paths for `audit_events`. On Postgres it's also DB-enforced: the services connect as a runtime role that owns nothing and holds only SELECT/INSERT on `audit_events` and `operator_actions` (DELETE on no table), granted by the migration step (`agentguard.audit.grants`). Because the runtime role isn't the owner, it can't grant itself UPDATE back — an earlier single-role setup could, which `tests/test_db_grants.py` now checks against real Postgres. Scope: protects against a misused app connection, not a privileged DB superuser or role reassignment — no "unbreakable log" claim. Not applied to SQLite dev/test runs (no equivalent grant model) | 1 (code path), 5 (DB grant) |
| 2a | Agent lies about which tenant a resource belongs to | `resource_tenant_id` is the agent's claim and only feeds an early tenant check. The real boundary is enforced by the target on the actual record: the broker sends the *verified* tenant, and the helpdesk treats another tenant's ticket as missing (live-stack test) | 8 |
| 8a | Untraceable operator actions | Human actions taken in the console (approval decisions, suspend/resume) are written to the append-only `operator_actions` table with the authenticated actor; approval decisions also land in `audit_events` against the execution. The same REVOKE script covers `operator_actions` | 6 |
| 9 | Sensitive data in traces | `executions` and `audit_events` store only hashes of request/result payloads; full arguments live in the separately-restrictable `request_payloads` table; OTel span attributes carry identifiers and decisions only (tested) | 1, 4 |
| 10 | Duplicate tool call | Gateway dedupes on (agent, idempotency key); the target system dedupes on the execution id, which is globally unique — agent-supplied keys aren't, so two agents' keys can't collide downstream (tested) | 1, 4 |
| 11 | Confused deputy (broker misuses its own privilege) | Broker only acts on a decision the policy engine already produced, and each executor gets a credential for one scope only, enforced by the target system. The broker service also re-reads the recorded execution before using a credential — it must exist, be allowed (or approved with its approval consumed), name this executor and tenant, carry exactly these arguments, and not have finished — so a stolen broker service token alone can't make it act (live-stack test) | 1, 4, 8 |
| 12 | Approval from wrong tenant/role | Approver identity and authority are checked server-side against the execution's tenant/role requirement, not trusted from the approval request itself. Through the operator console (`/v1/console/approvals/{id}/decide`) the approver's name, role and tenant come from the bearer token's configured principal; `x-approver-*` headers are ignored, and all-tenant *read* access (`*`) never grants approval authority (`tests/adversarial/test_console_approvals.py`). The older header-based `/v1/approvals/{id}/decide` endpoint has been removed (test asserts it stays gone) | 1 (enforcement), 2 (adversarial test), 6 (console) |
| 13 | Schema drift on tool arguments | **Partial.** Arguments a `write-high` or `destructive` tool doesn't declare in its `input_schema` are denied before policy (`gateway/validation.py`; adversarial and demo-traffic cases). Lower-risk tools let extra fields through, and argument *types* aren't checked by the gateway; the target system validates its own inputs (the helpdesk rejects malformed refunds) | 1, 5 |
| 13a | A policy change quietly loosens enforcement | Publishing from the console needs the operator role and all-tenant read access. The server re-simulates the proposal against every recorded call and refuses one that newly allows denied or gated calls unless the operator acknowledges it with a reason. It chooses the version number itself, unique in the database. Rules with unknown match keys or operators are rejected, because the engine would otherwise ignore them and widen the rule. Every publish, with its simulation summary, goes to `operator_actions`, and approvals issued under the old version can't execute afterwards (`tests/adversarial/test_console_approvals.py`). It doesn't stop an operator who acknowledges a loosening deliberately; it makes that decision explicit and attributable | 6 |
| 14 | Agent loop / tool-call spam | Per-agent rate limit, rolling spend budget, circuit breaker on repeated denials, per-agent suspend, and a global kill switch; plus broker timeouts as per-call deadlines (all tested) | 4 (implemented) |
| 15 | Model update changes agent behavior | Regression suite (routine + adversarial cases) required to pass before any prompt/model/tool/policy change ships | 2 |
| 16 | Replay accidentally triggers a real action | Three layers: (a) `agentguard.replay` never imports `agentguard.broker` or the gateway service, verified by a test that inspects loaded modules in a fresh interpreter; (b) tool steps run through dry-run adapters only; (c) the CLI's DB connection is read-only at the database level (`PRAGMA query_only` / `READ ONLY` transactions) | 3 (implemented) |
| 17 | Clock skew / missing trace segments | `trace_complete` is explicitly computed and false when a segment is missing (e.g. unresolved timeouts), and events correlate by execution id. The broker service reports its own start/finish times on every execution; the gateway checks they fall inside its own send/receive window (within `CLOCK_SKEW_TOLERANCE_SECONDS`) and, if not, records a `clock_skew` audit event that the anomaly report surfaces (`tests/test_clock_skew.py`). It detects skew between the two services; it doesn't correct timestamps, and the in-process broker mode has only one clock | 1, 9 |
| 18 | Partial failure in a multi-step workflow | Agents label the steps of one task with a `workflow_id`. The label only groups calls: it's scoped to the calling agent and never affects a decision. The console's Workflows view (`/v1/console/workflows`) classifies each one as completed, waiting (approval pending), stopped (nothing written, safe to retry) or partial (a write happened, or may have, and a later step didn't), and lists exactly which writes took effect (`tests/test_workflows.py`). Compensation is a human decision from that list. There's no automatic rollback, because the target's actions (refunds) have no safe automatic inverse | 9 |

## Non-claims

This system does not claim to be "the first AI agent security platform" or to produce an "unbreakable audit log." The audit mechanism reduces tampering risk through restricted write permissions and (optionally, later) external immutable storage — it does not claim to stop every privileged attacker, and that limitation should stay stated plainly in any writeup.
